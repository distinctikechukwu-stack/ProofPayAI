# Cloudflare PayPal Sandbox webhook processor

## Status and architecture

This is local implementation and test preparation only. No Cloudflare resource, secret, PayPal webhook, provider operation, or Staging record has been changed. The Worker is intended for the Staging Supabase project `whdvvbwirfmdubrlzaxo` and PayPal Sandbox only.

Cloudflare Worker exposes `POST /api/webhooks/paypal`. It bounds the request body, parses the PayPal event, requires the transmission headers, and uses the existing `PaypalClient.verifyWebhook` against the fixed PayPal Sandbox API host. Only the seven existing invoice event types are eligible for durable enqueue. After signature verification, it calls the existing service-role-only `enqueue_verified_paypal_webhook` RPC and returns HTTP 202 only after a valid durable receipt.

Supabase remains the source of truth and the event ledger. Cloudflare Queues carries only a drain-verified-inbox hint; it does not carry webhook payloads, invoice identifiers, credentials, or user information. The Worker drains rows through PaypalWebhookWorker, which claims events with a database lease, fetches the invoice from PayPal Sandbox, and submits the provider-confirmed snapshot to complete_verified_paypal_webhook. PayPal Invoicing v2 audit metadata is nested at detail.metadata. The parser uses detail.metadata.last_update_time as the provider-maintained version and accepts detail.metadata.update_time only as a compatibility fallback when the canonical field is absent. A present malformed timestamp rejects the provider snapshot; local observation time is never substituted as the provider version. The provider version is persisted separately from provider_observed_at. Transactional Migration 20 rejects older versions, makes equal-version acceptance conditional on matching internal and raw provider states, prevents versionless snapshots from replacing versioned rows, and adds database guards for invalid status transitions. It has not been applied to Staging.

The Worker sends a queue wake signal after a successful enqueue receipt that is still pending. If that send fails after Supabase commits, it still acknowledges with 202; the once-per-minute Cron sweep recovers the durable row. Each Cloudflare Queue invocation drains at most eight Supabase events and emits another wake hint when the cap is reached. Queue batch size remains one wake message; it is separate from the eight-row database drain cap. The Cron path drains at most one event. Errors that escape Queue orchestration cause Cloudflare message retry. PayPal or Supabase processing failures remain in Supabase retry/dead-letter state; the Cloudflare DLQ contains wake hints only.

The scheduled trigger runs independently of Render and recovers missed wake messages. Cloudflare's event-driven Queue consumer does not poll an empty Queue. The Cron sweep checks at most one database event each minute; if the pass reaches its cap it wakes the Queue consumer to continue the backlog. The 60-second Cron interval bounds normal missed-wake latency but does not guarantee delivery during Cloudflare, PayPal, or Supabase outages. When Cloudflare is activated, confirm the Render webhook worker is stopped/disabled first. Database leases protect rows if processors overlap, but they are not a substitute for a single-processor cutover.

`GET /health` reveals only `status` and a boolean configuration-presence result. It does not make provider or database calls. Logs use fixed stage/error codes and an allowlist; they do not log headers, signatures, event bodies, provider responses, access tokens, service keys, or invoice URLs.

```powershell
npm run test --workspace @proofpay/api -- paypal.test.ts paypal-webhook-worker.test.ts cloudflare-paypal-webhook.test.ts
npm test

npm run build
npm run cloudflare:webhook:dry-run
```

The example `.dev.vars.example` contains placeholders only. For local Worker testing, create `apps/cloudflare-paypal-webhook/.dev.vars` yourself with non-production test secrets in a private local file; never commit it. Do not use real credentials in shared logs or chat. Wrangler requires the three bootstrap secrets (Sandbox client ID/secret and Staging service-role key). `PAYPAL_WEBHOOK_ID` is deliberately omitted from `secrets.required` so the initial Worker can be deployed before PayPal registration; the handler still requires it at runtime and fails closed until it is present. Set it only after the callback has been registered; Wrangler secret updates create and deploy a new Worker version.

`wrangler deploy --dry-run` validates the bundle and Wrangler configuration without publishing a Worker. Do not run `wrangler deploy`, `wrangler secret put`, queue creation, or dashboard changes as part of local verification.

For the no-secrets Linux Workerd smoke, run npm run cloudflare:webhook:smoke from CI after dependencies are installed. The script checks only whether secret-file paths exist, launches Wrangler with an allowlisted environment, verifies /health returns status=ok and configured=false, invokes the local scheduled-Cron route while unconfigured, and checks that an unconfigured webhook fails closed. It makes no provider or database requests. Synthetic Queue and Cron handler behavior is separately covered by the API test suite; the Workerd smoke does not exercise actual Queue delivery.

## Retry, dead-letter, and monitoring model

- Supabase `paypal_webhook_events` is authoritative for event processing state and retries. Inspect status, attempt count, next-attempt time, sanitized failure code, lease expiry, and dead-letter status through an approved operator view/API. Do not query or display payload JSON for routine monitoring.
- Cloudflare Queue metrics show only wake-hint backlog/delivery attempts. A DLQ entry indicates a repeatedly failing drain notification, not a lost or dead-lettered PayPal event. Check Supabase queue state after any Queue DLQ alert.
- A missed queue hint is recovered by the Cron sweep. A worker crash during a leased event is recovered after the DB lease expires. The configured queue retry delay is 60 seconds; Cron recovery operates independently.
- Current implementation has no authenticated operator dashboard or endpoint. For a Supabase dead letter, first inspect only its event-row UUID, event type, resource ID, attempt count, failure code, lease/dead-letter timestamps through an approved protected operator path; do not read raw payload JSON for routine recovery. Confirm the provider/configuration fault is fixed and verify the linked invoice through an authorized reconciliation path. Then, from a trusted server-side operator tool using the service-role credential from the secret manager, call the existing service-role-only `requeue_dead_lettered_paypal_webhook(event_row_uuid)` RPC. It resets retry metadata and makes that same verified row eligible again; it does not create a new event or mutate invoice state. A true result means the next Cron/Queue drain can claim it; confirm the subsequent attempt and processed/dead-letter state through approved metadata-only monitoring. If no protected server-side operator tool is available, stop and coordinate one; do not expose the RPC or service-role key through a browser or public route.

Ingress abuse controls currently in code are request-body, content-type, header-length, route/method, and Sandbox certificate-host validation, followed by provider signature verification before any durable write. Timeouts bound the signature and enqueue calls. There is no Worker-local IP counter or configured edge rate-limit rule. Do not add an in-memory counter: it is neither global nor durable. Before activation, review the current Cloudflare account's WAF/rate-limiting entitlement and consider a conservative edge threshold for malformed or repeated traffic. Do not block PayPal's legitimate retries or valid deliveries based on an unverified IP allowlist; keep 5xx responses retryable when verification or durable enqueue is unavailable. Monitor rejected requests, PayPal delivery retries, and queue/database backlog together. Any edge rule is an external configuration change and needs separate approval.

## Reliability, plan limits, and costs

Cloudflare Workers and Queues avoid Render Free instance sleep for the ingress and scheduled processing path, but still depend on PayPal and Supabase availability. PayPal delivery is at least once and retries non-2xx responses; the durable Supabase enqueue remains the only point after which the receiver returns success. Supabase or PayPal outages leave event state in the existing database retry schedule. Cron resolution is one minute, so a missed Queue wake can add up to one minute of recovery latency when services are available. A Cloudflare incident or missing/invalid secret can still delay processing. This branch includes a local-only migration for provider-version ordering; the Worker is not safe to activate until that migration has passed database-engine validation and is later applied through the approved Staging process.

Cloudflare documentation currently lists these relevant Free-plan limits: Workers allow 100,000 requests per day, HTTP and Cron invocations have 10 ms CPU, and a Worker invocation is limited to 50 external subrequests. Queues allow 10,000 standard queue operations per day, retain messages for 24 hours on Free, and accept messages up to 128 KiB, and support up to 100 consumer retry attempts. This Worker configures five retries with a separate dead-letter queue. Queue consumers have a 15-minute wall-clock limit and a 30-second default CPU budget; increasing it to five minutes is a Paid-plan option, not evidence of Free-plan CPU headroom. This Worker deliberately keeps Queue batches at one wake message, drains at most eight durable database rows per Queue invocation, and drains at most one row per Cron invocation. The no-secrets Workerd smoke and Wrangler dry run do not measure Free-plan CPU headroom or real service quotas. Recheck account-specific quotas, pricing, and current platform limits before activation; no upgrade or charge has been authorized.

Cloudflare Workers Free currently limits external subrequests to 50 per invocation. Estimated maximums for this implementation, counting each Supabase RPC as one external fetch and assuming no provider redirects or hidden retries:
- Ingress: at most three external fetches on a cold request: PayPal OAuth, PayPal signature verification, and Supabase durable enqueue. Queue binding send is counted separately as Queue usage.
- Queue consumer: at most eight database rows per pass. A normal row uses one claim RPC, one PayPal invoice GET, and one completion or retry RPC; a cold PayPal OAuth adds one fetch for the invocation, and the loop makes one final empty claim. This is 26 external subrequests in the normal full-pass case. If every invoice completion call fails and also schedules a retry, the estimate is 34. Repeated OAuth failures do not exceed that estimate because each failed read is followed by a retry RPC rather than an invoice GET.
- Cron: one event per pass, approximately five external fetches (claim, cold OAuth, invoice GET, completion, then one empty claim); an additional retry RPC can bring the pass to six.

The eight-row database cap is independent of Wrangler `max_batch_size: 1`, which limits wake messages delivered to a Queue invocation, not Supabase rows claimed. These calculations are an upper-bound estimate from code paths, not an observed Cloudflare metric; redirects or future HTTP retries add subrequests. The cap leaves at least 16 requests below the Free 50-subrequest limit in the identified Queue completion-failure path. Queue sends still consume Queue operation quota.

## Test scope and limitations

Automated tests use synthetic webhook JSON, synthetic credentials, mocked PayPal verification/invoice reads, mocked Supabase RPCs, and mocked Queue messages. They cover valid/invalid signatures, body validation/size, durable-receipt gating, duplicate delivery, queue-send failure after commit, Queue retry/DLQ configuration, continuation, Cron recovery, and secret/config boundaries. No real provider, remote database, Render, or Cloudflare service is contacted and no invoice is created. The pgTAP suite executes actual migration-20 RPC and trigger paths against local PostgreSQL when the manually dispatched Ubuntu workflow is run. A two-session test applies newer REFUNDED before an older PAID snapshot and checks the final invoice and event rows. Neither PostgreSQL nor Docker is installed in the current Windows environment, so these database-engine tests remain unrun locally.

The Worker imports Node.js compatibility APIs for cryptographic UUID generation and Basic authentication; Wrangler bundle dry-run alone is not runtime evidence. A Workerd smoke was attempted on Windows and failed before handler startup with an access violation/stack overflow. The new Linux-only no-secrets smoke is prepared for the validation workflow, which can run only on a push to `codex/cloudflare-paypal-webhooks` or by manual dispatch with that branch selected; it has not run here. If it passes, that proves only Worker runtime startup, the health response, fail-closed behavior while unconfigured, and local Cron invocation. It does not prove Queue delivery/retries/DLQ, external Cron activation, Free-plan CPU headroom, Supabase network/auth policy, PayPal Sandbox credentials, genuine signature verification, or authoritative payment reconciliation. Queue and Cron handler logic is covered separately with mocked synthetic messages.

## Rollback

1. Stop the Cloudflare Queue consumer and Cron trigger, and remove/disable the PayPal Sandbox webhook endpoint only after separately approved operator action. Keep the Worker deployed until ingress is no longer registered and in-flight queue/database leases have drained or expired.
2. If returning to Render processing, confirm the Render webhook ID/configuration and worker health through its masked configuration/status, then enable only that processor. Do not enable both processors intentionally.
3. Do not delete Cloudflare Queues, Supabase webhook rows, leases, retries, dead letters, or invoice records during rollback. Preserve them for reconciliation.
4. Compare pending DB events, retries, and dead letters before declaring rollback complete. Re-register or reconfigure only after separate approval and normal change review.
5. Migration 20 is transactional, but do not run a destructive down script: provider_updated_at is the ordering evidence and must be preserved. A future schema rollback requires a reviewed compensating migration that retains provider-version data and coordinates the trigger and RPC. The new completion RPC keeps its trailing provider timestamp parameter optional, so old seven-positional-argument SQL calls remain syntactically valid; that is not full behavioral compatibility. A legacy processor that omits provider_updated_at cannot replace a row once a provider version exists. Keep a compatible processor active and do not cut back to a legacy worker until its snapshot behavior has been updated and reviewed.

No external activation step above has been executed.
